# Hannibal: learned search experiment

Implementation: `client/src/bots/strategies/hannibal.ts`. Selectable through the normal `BOTS`
catalog as `hannibal`.

## What is actually learned?

A **27-weight logistic value model**, trained locally from game outcomes. This is not a
fine-tuned language model or a full AlphaZero implementation. The compact model runs in
TypeScript, offline, without a GPU, model runtime or API request.

Inputs describe both armies: king health/exposure, material, endangered soldiers, direct
attacks, focus fire, development, protection, energy, springs, towers and unit counts.
Features are antisymmetric under side exchange and independent of seed, pawn ids and map size.
`league-v1` is a stable checkpoint, checked against the feature schema at load time.

Training used **80 games / 5,483 positions**, generated by a league of Easy/Normal/Hard
depthsearch, Napoleon Normal and Random bots. It is supervised outcome learning from
league games, not self-play policy training. The trainer fits weights with full-batch Adam
and retains the best checkpoint on a validation split by whole game. Validation log loss
improved from **0.4167 to 0.3233**. Four capped training games were labeled 0.5; these are
censored outcomes, not demonstrated draws. Training identities use `value-training-v1-*`.

## Search

- PUCT/MCTS over complete activations, using the value model for candidate ordering and
  evaluation. Priors are derived from value estimates; there is no separately trained policy.
- Ownership follows actual initiative, including consecutive allied activations. Values
  always belong to the decision's root side.
- Candidate selection considers alternate signatures before final tactical reranking.
- Terminal outcomes propagate through search. Universal solved claims require all legal
  successors, so a truncated beam is not mistaken for a proof.
- An exact next-enemy-turn regicide check filters unsafe root plans where alternatives exist.
  This does not prove safety against a whole enemy army sequence.
- After inactive rounds, a small configurable progress term discourages endless retreat.
  This is a handwritten anti-stall addition, not a trained reward.
- The real random stream is never used to predict future Hellfire.

`backup: "average"` is the tested default. The alternative minimax backup was less effective
in the initial experiments and remains available for explicit comparison.

## Parameterization

```json
{
  "name": "hannibal",
  "options": {
    "model": "league-v1",
    "simulations": 128,
    "candidates": 16,
    "exploration": 1.4,
    "horizon": 16,
    "backup": "average",
    "pressure": 0.1
  }
}
```

Presets expose 32 / 128 / 512 / 2,048 simulations and increasing candidate/horizon limits.
Constructors own validation and immutable options. Configurations use the shared catalog,
URL and snapshot contract; future checkpoints can use the same interface.

More compute is **not yet monotonically stronger**. In the same frozen test, 128 simulations
outperformed 512. The 2,048-simulation sample improved some finishes but had multi-second
decision latency. These are experimental presets, not validated difficulty rankings.

## Benchmarks

All matches use equal centrally symmetric armies, play both bot sides, and cap at 360
activations. The opponent is depth-four Hard, beam 6, unless stated otherwise. Timeouts
are reported separately; “match score” treats them as half a point only for comparison.
Training, tuning, confirmation and frozen-test seed prefixes are distinct.

| Experiment | Simulations | W–L–timeout | Score |
| --- | ---: | --- | ---: |
| Tuning set, 8 paired games | 512 | 11–3–2 | 75% |
| Confirmation, all 4 biomes, 3v3 / 5v5 / support 5v5 / 7v7 | 512 | 24–5–3 | 79.7% |
| Frozen test, all 4 biomes, 3v3 and support 5v5 | 512 | 13–2–1 | 84.4% |
| Same frozen test | 128 | **14–2–0** | **87.5%** |
| Fresh 3v3 across 4 biomes, depthsearch beam **32** | 512 | 7–0–1 | 93.8% |
| Fresh 3v3 across 4 biomes, Napoleon Brutal | 512 | 4–2–2 | 62.5% |

Learning ablation on the first eight tuning matches with identical 512-simulation search:
trained model **6–1–1**, handwritten baseline model **3–4–1**. Outcome fitting contributes
to strength; it is not just spending more search time.

Frozen test at 128 simulations: Hannibal p95 **68 ms**, worst **266 ms**; depthsearch p95
**111 ms**, worst **856 ms**. Timing is native Node on this workstation, not a mobile guarantee.
The large-search confirmation sample reached p95 **2.77 seconds** at 2,048 simulations while
other benchmarks ran concurrently. The 512-simulation confirmation was split after the
shell's 10-minute cap; all 32 matches completed across the two runs.

These samples are encouraging and substantially better than Napoleon's initial 6–5–1.
They do not establish universal dominance or an 80% lower confidence bound. Hell, asymmetric
maps, every possible roster and fair wall-clock tournaments still need broader evaluation.
No campaign is switched to this bot on the strength of these experiments alone.

## Reproduce

### Automated retraining after a gameplay change

```sh
make retrain-value ARGS="--config=scripts/value-training.example.json --output=training-runs/update-001"
# Any scalar can be overridden; longer runs do not change CI or push-hook work.
make retrain-value ARGS="--output=training-runs/update-002 --training.games=800 --training.epochs=2000 --evaluation.pairs=32 --evaluation.search.simulations=128"
```

Paths are relative to `client/`, because Make invokes npm there. JSON configuration supports
partial nested overrides, including full training `league` and evaluation `opponents` arrays
of ordinary `{ name, options }` bot configurations. Unknown fields, invalid budgets and
overlapping seed prefixes are rejected before a run starts.
`scenarios.rosters` and `scenarios.biomes` select the armies and terrain used for both
datasets; they are validated with the engine's setup contract. Include new units explicitly
after adding them to the game.

The pipeline generates fresh league games, excludes timeouts by default (`training.timeouts`
can explicitly select `draw`), splits by whole game, fits a checkpoint, then plays paired
evaluation matches against the configured opponents and optionally the incumbent. Training
and evaluation are sequential, so inference timing does not compete with model fitting.

Each new run directory contains `config.json`, `provenance.json`, `samples.json`,
`candidate.json` and `report.json`. Existing directories are rejected to preserve results.
Artifacts are ignored by Git. The incumbent checkpoint is never overwritten. A failed
strength, validation, timeout or latency gate exits nonzero but retains all evidence.
Evaluation timeouts receive **zero** score credit, unlike the early exploratory benchmarks.
The incumbent gate has its own `incumbentMinScore` (default 0.5); other opponents use
`minScore` (default 0.75).

An accepted candidate is ready for review, not automatically released. Register a new stable
model id before promoting it; gameplay replay identity should retain the checkpoint that was
actually used. Feature/action schema changes may need code changes before retraining.

Normal CI never runs training or tournaments. Unit tests exercise fitting on tiny synthetic
samples and validate configuration/acceptance rules. Pre-push runs the existing fast client
and Go checks. Full integration remains in CI's AI job.

### Original experiment commands

```sh
GAMES=80 make train-value
PREFIX=value-frozen-test STRIDE=2 PAIRS=8 SIMULATIONS=128 make bench-hannibal
PREFIX=value-confirmation PAIRS=16 SIMULATIONS=512 make bench-hannibal
PREFIX=value-timing STRIDE=4 PAIRS=4 SIMULATIONS=512 LEGACY_BEAM=32 make bench-hannibal
MODEL=baseline PAIRS=4 SIMULATIONS=512 make bench-hannibal
make check
```

`train-value` overwrites the local checkpoint; benchmark prefixes and scenario selection
are explicit. Retraining a released checkpoint should create a new stable model id.

## Could this be a Mistral fine-tune?

The [current hosted fine-tuning documentation](https://docs.mistral.ai/resources/deprecated/finetuning)
marks that API deprecated and no longer actively supported (checked October 12, 2026).
Do not build this experiment around availability of that legacy service.

Self-hosted fine-tuning of an open-weight Mistral model is a different project. The engine
could supply position descriptions, candidate plans and search-improved labels for supervised
training. A model would choose a legal plan id; the engine would still execute and validate it.
That needs substantially more compute and has much higher inference cost than this evaluator.

The next local learning step is a richer small neural value model plus a separately trained
plan policy, with fresh self-play and loss-position mining. First preserve the current
checkpoint and frozen tests, and resolve the non-monotonic search scaling before increasing
model size.
